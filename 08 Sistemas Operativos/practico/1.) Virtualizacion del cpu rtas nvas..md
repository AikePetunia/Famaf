b. ¿Porqué a veces el cputime es menor que el walltime?

Tenemos que el walltime/realtime es el tiempo que tomo en la vida real (Desde que el proceso se creó hasta que finalizo).

El Cputime/usertime es el tiempo que el procesó costo en el procesador, o sea todo el tiempo que ocupo literalmente el proceso en procesarse en el procesador. 
Notemos que el proceso en si, en cputime cuesta en promedio 2.50s.

Cada proceso, tiene 3 estados principales.
Ready, Running y blocked. 
En un sistema operativo en general, el walltime supera al de cpu por 2 cosas: espera tiempo a pasar a running, o blocked (espera I/O (disco, red o teclado)).

El comando de shell está dado por `&`, o sea por segundo planos, permitiendo que las instancias/procesos puedan acumularse, y permite que NO se espere a que el otro proceso termine, si no que empieza uno atras del otro, una instancia se libera apenas se termina de calcular la otra. Onda:

Debido al Time-Sharing (Tiempo compartido) del procesador, que permite que los nucleos del procesador se puedan compartir en varios procesos para poder correr varios procesos (virtualizacion de cpu), que termine correr más procesos por mas que tengamos pocos nucleos, hace que los nucleos se tenga que dividir entre varios procesos. Ejercicio 4. Un programa define la variable int x=100 detro de main() y hace fork(). 
(a) ¿Cu´anto vale x en el proceso hijo? 
La syscall fork(), duplica un proceso actual (y su contexto, tales como variables). 
Haciendo que el programa que creo el fork(), (el padre), nazca su hijo apartir de la duplicacion del padre por el fork().

Probablemente, el codigo tenga algo como:

```bs 
int x = 100;
fork();
printf("hola, %d", x); // <- Esto lo ejecutaran el proceso padre y el hijo
```

(b) ¿Qu´e le pasa a la variable cuando el proceso padre y el proceso hijo le cambian de valor? 

Si el padre modifica una variable, se verá afectada en el hijo.
Si el hijo modifica una variable, no se vera afectada en el padre.
