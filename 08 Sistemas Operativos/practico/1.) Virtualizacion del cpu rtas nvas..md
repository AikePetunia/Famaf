Ejercicio 4. Un programa define la variable int x=100 detro de main() y hace fork(). 

(a) ¿Cu´anto vale x en el proceso hijo? 

La syscall fork(), duplica un proceso actual (y su contexto anterior a la syscall fork(), tales como variables u otras cosas), ademas de que la llamada puede retornar:
fid == -1 si hubo algún error en la llamada fork()
fid == 0 si estoy en el proceso hijo.
fid > 0 si aún estoy en el proceso padre.
 
Trabajar dentro de un if() para cada valor de fid devuelto es lo mejor que hay para manejar contextos distintos en cada proceso nuevo. 

El creador del fork, se le llama proceso padre y el proceso creado a partir del padre se llama hijo, siendo este proceso hijo casi similar al proceso padre, causando algo como:

```c 
int x = 100; // <- contexto anterior
fork();  // <- Proceso padre crea su hijo
printf("hola, %d", x); // <- Esto lo ejecutaran el proceso padre y el hijo (ademas de la variable x)
```

Por lo tanto, ambos programas queda x=100.

(b) ¿Qu´e le pasa a la variable cuando el proceso padre y el proceso hijo le cambian de valor? 

Reitero que la syscall fork(), hace una duplicación del programa, una copia casi igual al proceso origianl, por lo tanto en un inicio pueden ser identicos, pero el contexto de cada proceso puede cambiar radicalmente.

Asumiendo que ya el problema se plantea luego de hacer un fork(), cada proceso tiene su propio contexto, por lo tanto el modificar una varialbe dentro del hijo o el padre no tendría por que afectar al otro, pero todo esto dentro de una buena practica. Pues:

```c
int x = 100; // <- contexto anterior
int fid = fork();  // <- Proceso padre crea su hijo
printf("valor de x:", %d) // 100 (Esto se imprimira 2 veces; en el hijo y en el padre)
if (fid == -1) {
	// error idk
} else if (fid == 0) {
	printf("VALOR DE X ANTES DE CAMBIARLO EN HIJO", %d); // 100
	x = 101; // este cambio solo existe en el hijo
	printf("valor x: %d", x); // 101
} else if (fid > 0) {
	printf("VALOR DE X ANTES DE CAMBIARLO EN padre", %d); // 100
	x = 102; // este cambio solo existe en el padre 
	printf("valor x: %d", x); // 102
}

```

(c) Contestar nuevamente las preguntas si el compilador genera ASM colocando esta variable en un registro del microprocesador.

(a): `x` sigue valiendo 100 en el hijo. La syscall `fork()` guarda el contexto completo de registros de la CPU en la estructura del proceso (`PCB` / `trapframe`) y lo duplica para el hijo. Por ende, el hijo restaura los mismos valores de registros.

(b): El comportamiento **no cambia en absoluto**. Cada proceso tiene su propio estado de registros virtualizado por el mecanismo de _Context Switch_. Cuando el hijo modifica el registro, solo altera su propio juego de registros; el padre conserva intacto el suyo cuando vuelve a tomar la CPU.

Ready - (Scheduled) -> Running:

Running - (IO: Initiate) -> Blocked:

Ahora, entendiendo el funcionamiento de cada flecha, nos hacemos facilmente una mejor idea de como funcionaria.

Ready - (Scheduled) -> Running:
El sistema operativo nunca puede preparar un programa para su ejecucion de instrucciones. Acerca de como funcionaria, el sistema operativo en si quedaria inutilizabe pues nunca podriamos volver a correr nuevos programas, no pudiendo hacer algo con el. Dejando el procesador en idle, no ejecutando nada, ningun proceso recibe tiempo de cpu.

Running - (Descheduled) -> Ready:
Sabemos que los procesos en el sistema operativo en realidad van medios asincronos y se ejecuta uno por vez, si sacamos esta flecha se saca esta posibilidad (Multi-tasking), perdiendo la capacidad de sacar cpu (A no ser que se vaya a blocked esperando IO)

Running - (IO: Initiate) -> Blocked:
El programa nunca podria recibir IO, o sea nunca podria leer un input o output de cualquier tipo, quedarian 100% cpu y no tendrian apoyo de ningun dispositivo (no duerme el programa esperando inputs o outputs), no pueden leer memoria, interacciones o demas, quedando en busy waiting

Blocked - (IO: done) -> Ready: 
El programa NO puede responder a los IO, puede recibir, hacer algo con memoria o teclados, pero el usuario tendria que re abrir los programas por cada vez que se recibe un io, por ejemplo, cargar algo de memoria, un input o output, etc. Por que no tiene manera de despertar el proceso diciendole "eu mira ya tenes lo que querias", quedando atrapado en el blocked.

- **Sin `Scheduled`:** SO inútil (CPU ociosa para siempre).
    
- **Sin `Descheduled`:** Se pierde la multitarea preentiva (sin _time-sharing_).
    
- **Sin `IO: Initiate`:** Se pierde la I/O por interrupciones y se fuerza la espera activa (_busy waiting_).
    
- **Sin `IO: Done`:** Los procesos quedan atrapados eternamente en estado _Blocked_.

Ejercicio 11. 
Dentro de xv6 el archivo x86.h contiene struct trapframe donde se guarda toda la informaci´on cuando se produce un trap. Indicar que parte es la que apila el hardware cuando se produce un trap y que parte apila el software.

Sabemos que un trap se produce cuando se va cambiadno de modo usuario a modo kernel. O sea que un trap por asi decirlo, es la manera de definir la transicion de usermode a kernelmode, esto sucede cuando se hace una syscall.

Cuando el sistema operativo inicia, se crea un trap table para guardar un registro de los programas que hacen un trap (LDE), para saber a donde volver cuando ocurre un return-from-trap.

```c
struct trapframe {
  // --- APILADO POR SOFTWARE (trapasm.S vía pushal) ---
  uint edi;
  uint esi;
  uint ebp;
  uint oesp;      
  uint ebx;
  uint edx;
  uint ecx;
  uint eax;

  // --- APILADO POR SOFTWARE (trapasm.S) ---
  ushort gs;
  ushort padding1;
  ushort fs;
  ushort padding2;
  ushort es;
  ushort padding3;
  ushort ds;
  ushort padding4;

  // --- APILADO POR SOFTWARE (vectors.S) ---
  uint trapno;

  // --- APILADO POR HARDWARE (o software si no hay err) ---
  uint err;

  // --- APILADO POR HARDWARE (CPU x86) ---
  uint eip;
  ushort cs;
  ushort padding5;
  uint eflags;

  // --- APILADO POR HARDWARE (solo si venía de User Mode) ---
  uint esp;
  ushort ss;
  ushort padding6;
};
```

- **Hardware (CPU x86):** Apila automáticamente `ss`, `esp` (si hubo cambio de anillo de privilegio), `eflags`, `cs`, `eip` y, en ciertos casos, el código de error `err`.
    
- **Software (xv6):** Apila el número de trap (`trapno`), completa el `err` si el hardware no lo puso, guarda los registros de segmento (`ds`, `es`, `fs`, `gs`) y guarda todos los registros de propósito general con `pushal`.

Cada proceso tiene una memoria virtual distinta (aka: distintos universos por asi decirlo), pueden quiza referencia 0x2000 pero no va a ser el mismo bloque, por lo tanto si pueden.
El MMU y las tablas de paginas del kernel se encargan de traducir esa misma direccion virtual en una distinta direcion fisica

(c) Para guardar el estado del proceso es necesario salvar el valor de todos los registros del microprocesador. 
Para poder pausar un proceso y reanudarlo más tarde exactamente en el mismo punto sin alterar su ejecución, **el SO/hardware debe guardar obligatoriamente el estado de los registros del microprocesador** (EAX, EBX, EIP, EFLAGS, ESP, etc.) en el PCB (_Process Control Block_) o en la pila del kernel.

(d) Un proceso puede ejecutar cualquier instrucci´on de la ISA. F
No, para eso necesita modo Kernel para poder ejecutar instrucciones de hardware. para eso se exponen las syscalls. El user mode puede ejecutar instruccines de ISA no privilegiadas


(e) Puede haber traps por timer sin que esto implique cambiar de contexto. V

- El temporizador interrumpe la CPU y salta al kernel (cambio de modo).
- El _scheduler_ revisa si el proceso actual consumió su _quantum_.
- Si el proceso todavía tiene tiempo asignado o no hay otros procesos en _Ready_, el SO simplemente responde a la interrupción y vuelve a ejecutar el **mismo proceso** (`return-from-trap`), **sin hacer un cambio de contexto**.


(f) fork() devuelve 0 para el hijo, porque ning´un proceso tiene PID 0. F
fork da 0 para el hijo pero por mecanismo de la API, -1 para error y > 1 si es el padre.

(g) Las syscall fork() y execv() est´an separadas para poder redireccionar los descriptores de archivo. V
`fork()` y `exec()` están **separadas a propósito** para crear una ventana de tiempo entre la creación del proceso hijo y la ejecución del nuevo programa. En esa ventana (en el código del hijo, antes de invocar `exec()`), el _shell_ puede manipular los descriptores de archivo con `close()` y `dup()` para lograr la redirección (`>`, `<`) y los _pipes_ (`|`) de manera limpia y transparente para el programa que va a ejecutarse.

(h) Si un proceso padre llama a exit() el proceso hijo termina su ejecuci´on de manera inmediata. F
debe de usar wait para esperar a que el hijo termine su ejecucion y lueugo hacer un exit. La limpieza se hace de abajo para arriba por asi decirlo. Si no se hace, los procesos hijos quedan huerfaos 

(i) Es posible pasar informaci´on de padre a hijo a traves de argv, pero el hijo no puede comunicar informaci´on al padre ya que son espacios de memoria independientes. F
El hijo si puede comunicarse con el padre por los exit codes y el padre recibiendolo on un wait(). El padre debe de saber manejar los errores dejado por el hijo

(j) Nunca se ejecuta el c´odigo que est´a despu´es de execv() F
Se ejecuta  solamente en caso de error

k) Un proceso hijo que termina, no se puede liberar de la Tabla de Procesos hasta que el padre no haya le´ıdo el exit status via wait(). V
Cuando un proceso finaliza pero no se recoje su salida, se vuelve Zombi, su código de salida se conservan retenidos hasta que el proceso padre ejecute la llamada `wait()` o `waitpid()` para liberar (_reap_) su entrada.
